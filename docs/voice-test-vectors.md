# BlackVault Voice — Test Vector Fixtures (v1)

**Status:** KAT (Known Answer Test) fixtures for the protocol document.
These are the test vectors an external reviewer uses to verify that an
implementation matches the spec. They are NOT yet run against the
reference implementation (the implementation does not exist yet); the
implementer should produce the actual KAT outputs from a known-correct
implementation, paste them here, and verify that the reference
implementation reproduces them byte-for-byte.

---

## 1. Inputs to all fixtures

To make the vectors reproducible, all randomness in the KAT is replaced
with deterministic test data. In production, the values are generated
with `crypto.getRandomValues` (or the equivalent). The KAT uses
explicitly known byte sequences.

Hex notation is used throughout. Bytes are concatenated in order.

### 1.2 Test identities (deterministic)

```
# Caller identity (X25519, ML-KEM-768, Ed25519)
CALLER_ED25519_PUB =

# Callee identity
```

**NOTE TO THE IMPLEMENTER:** the actual hex values for the keys above are
generated by running the @noble libraries with a fixed PRNG seed (or by
using a published test vector from those libraries). They are filled in
by the implementer once a known-good reference exists. The placeholders
above make the structure clear; the implementation PR replaces them
with concrete bytes.

For the KAT, the implementer should:

1. Pick or generate a deterministic X25519 keypair
2. Pick or generate a deterministic ML-KEM-768 keypair (ML-KEM keys are
   large; one option is to use the @noble/post-quantum "fromSeed"
   constructor with a fixed 64-byte seed)
3. Pick or generate a deterministic Ed25519 keypair
4. Run the KEX per §4.2 of `PROTOCOL.md` and record every intermediate
   value

The resulting vectors should be reproducible from the seed alone, and
byte-identical across implementations that follow the spec.

## 6. SRTP KAT — AES-CM-128 (KAT fixture 5)

**Inputs:** `srtpMasterKey`, `srtpMasterSalt`, plaintext, SSRC, sequence numbers.

### 6.1 Key derivation (RFC 3711 §4.3)

```
srtpEncryptionKey = SRTP_MASTER_KEY         // 16 bytes, used as-is for AES-CM

srtpAuthKey = HMAC-SHA1(
  key: 0x00 || "SRTP-AES-CM-128-ICM" || 0x00 || SRTP_MASTER_SALT || 0x00 || 0x00 || 0x00 || 0x01 || 0x00 || 0x00 || 0x00 || 0x03 || 0x00 || 0x00 || 0x00 || 0x04,
  msg: SRTP_MASTER_KEY
)
// 20 bytes: SRTP_AUTH_KEY = <filled in by the implementer>
```

(The 14-byte SRTP_MASTER_SALT, the label, and the 0x00 0x00 0x00 0x01 ... 0x04
suffix are RFC 3711 §4.3 key derivation parameters. The implementer
should use a vetted SRTP library and verify the output matches.)

### 6.2 Encrypt (RFC 3711 §4.1, AES-CM counter mode)

**Test inputs:**
- SSRC = 0x12345678
- Sequence number seq = 0x0001
- ROC = 0
- Plaintext = "Hello SRTP" (10 bytes) || padding to 16 bytes
- Expected IV = (srtpMasterSalt XOR (SSRC || ROC || seq)) truncated to 16 bytes

**Expected output:**
- Ciphertext: <filled in by the implementer>
- Auth tag: <filled in by the implementer>
- Full SRTP packet: <filled in by the implementer>

### 6.3 Reorder test

Send three packets with seq=0x0001, 0x0002, 0x0003. Deliver in order
0x0002, 0x0001, 0x0003. Receiver should accept all three (within the
reordering window) and decrypt correctly. ROC stays at 0.

### 6.4 ROC wraparound test

Send packets 0xFFFE, 0xFFFF, 0x0000, 0x0001. The receiver should
increment ROC from 0 to 1 on receipt of 0x0000, and the IV construction
for 0x0001 should use ROC=1. This is the standard SRTP rollover test.

### 6.5 Out-of-window test

Send 0xFFFF then 0x0000 (advances ROC), then a late 0x0001. The receiver
should reject 0x0001 as out-of-window (assuming default 100-packet
reorder window, and 0x0001 is now in the previous ROC window). The
receiver must not crash; it must drop the packet silently.

## 8. Transcript binding test (KAT fixture 7)

A reviewer can verify the KEX is bound to the transcript by varying one
input at a time and confirming the safety number changes.

```
# Test 1: change CALLER_X25519_PUB by one bit
safetyNumber_1 = computeSafetyNumber(
  modifiedCallerX25519Pub,
  originalCallerMlkemPub,
  originalCalleeX25519Pub,
  originalCalleeMlkemPub,
  safetyNumberSeed
)
// Assert: safetyNumber_1 != SAFETY_NUMBER
// The expected safety number for a single-bit modification of any
// identity public key is the original + 50% Hamming distance, on
// average. Assert Hamming distance is in [10, 22] (i.e., roughly half).

# Test 2: same with MLKEM public key
# Test 3: same with callee keys
# Test 4: change the transcript hash (via the KEX inputs)
```

These tests catch subtle bugs where the safety number might not be
bound to all the inputs. A weak binding (e.g., only to the safety
number seed) would let a MITM produce a collision by manipulating a
single input.

## 9. Loss/reorder fuzz harness (KAT fixture 8)

This is not a KAT (no known answer) but a test that the implementation
handles adversarial packet patterns correctly.

```typescript
// Pseudocode
function fuzzHarness(seed: number, trials: number = 1000) {
  const rng = mulberry32(seed);
  for (let i = 0; i < trials; i++) {
    const session = newSrtpSession(srtpMasterKey, srtpMasterSalt, ssrc);
    const sender = newSrtpSession(srtpMasterKey, srtpMasterSalt, ssrc);

    // Generate 1000 packets of known plaintext
    const packets = Array.from({ length: 1000 }, (_, i) => {
      return sender.encrypt(plaintextForIndex(i), seq=i);
    });

    // Apply adversarial pattern
    const corrupted = applyPattern(packets, {
      dropRate: 0.10,
      reorderRate: 0.20,
      duplicateRate: 0.05,
      rng,
    });

    // Receiver must:
    // 1. Decrypt every packet that arrives within the reordering window
    // 2. Reject every packet that fails the auth tag (no crash)
    // 3. Never reuse a nonce (instrument the nonce derivation; assert uniqueness)

    for (const pkt of corrupted) {
      try {
        const pt = session.decrypt(pkt);
        // assert pt matches plaintextForIndex(pkt.seq)
      } catch (e) {
        // auth tag failure; expected for corrupted packets
      }
    }

    // Assert no two decryptions used the same (ssrc, roc, seq) triple
    assert unique nonces
  }
}
```

The harness runs against the SRTP implementation. A pass means: the
crypto layer is correct under realistic packet loss and reordering
patterns, and a malicious or buggy relay cannot cause nonce reuse.

## 10. How a reviewer uses these fixtures

1. **Implement the KEX per §4.2 of `PROTOCOL.md`** using the inputs in §1.
2. **Run the KAT** to verify the outputs in §2-5 match.
3. **Run the SRTP KAT** to verify the encrypt/decrypt round-trip and
   the ROC behavior.
4. **Run the fuzz harness** to verify adversarial robustness.
5. **Compare the outputs to the placeholders** in this document. If
   the placeholders have been filled in by a previous implementer,
   the new implementation's outputs must match byte-for-byte.

The placeholders are intentionally empty in the first version of this
document. The implementer's first task is to produce the actual KAT
values from a known-good reference implementation and fill them in.

## 11. Deterministic randomness (for the implementer)

To produce deterministic test keys, use the following seed:

```
TEST_SEED = 0x000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f
```

X25519 keys can be derived from any 32-byte seed via clamping. Ed25519
keys similarly. ML-KEM-768 keys in `@noble/post-quantum` are derived
from a 64-byte seed.

For the safety-number emoji display, the implementer must pick an
emoji alphabet. Until the implementer makes that choice, the
EMOJI_DISPLAY placeholder stays empty.
